# RepoFixLab：面向大模型 / Agent 开发的学习路径

## 学习目标

通过 RepoFixLab 掌握一个可落地的代码修复 Agent：模型如何决定下一步、如何安全调用工具、如何在反馈中修正补丁，以及如何证明最终结果可靠。学习目标不是背诵框架名词，而是能在面试中解释设计取舍、失败模式和指标。

## 岗位理解与面试挑战

目标岗位是大模型应用 / Agent 开发，而不是泛后端或单纯模型训练。面试通常不满足于“会调用模型”：更关注能否将模型放入可控闭环，并在真实失败条件下保持可靠。

| 面试官要验证的能力 | RepoFixLab 对应证据 | 常见追问 |
| --- | --- | --- |
| Agent 循环与规划 | ReAct 与阶段化修复工作流 | 为什么不让模型自由循环？何时停止？ |
| 工具调用与安全 | 控制面独占 Docker 权限、策略拦截与审计 | 如何应对提示词注入或越权命令？ |
| 评测与反馈闭环 | Worker/Evaluator 分离、F2P/P2P | 为什么测试绿了仍不一定算修复？ |
| 上下文、RAG 与记忆 | Issue、代码、搜索和验证反馈的证据选择 | 哪些信息放上下文，哪些放检索或记忆？ |
| 生产化工程 | 运行账本、令牌消耗、失败原因、复现能力 | 如何控制成本、定位失败、支持人工接管？ |

核心挑战是把每个结论说成可验证的工程事实：说明输入、状态、工具、边界、反馈和指标，而不是只报框架名或结果数字。

## 一句话介绍

RepoFixLab 是基于真实 GitHub Issue 的容器化代码修复智能体与可信评测平台。它把 Pi 的通用会话能力包装为 ReAct 式、阶段化的代码修复 Agent，并使用隔离的官方评测环境判断修复是否真正成立。

## 第一章：从 ReAct 到代码修复工作流

ReAct 的核心是“思考—行动—观察”循环：模型先根据当前证据决定动作，调用工具获得新信息，再更新下一步决策。RepoFixLab 将这个开放循环约束为可控阶段：

```text
理解问题 → 定位代码 → 制定计划 → 生成补丁 → 受控验证 → 修订 → 自审 → 官方评测
```

这样设计的原因：代码修复不是一次文本生成。模型必须读取仓库、缩小范围、提出假设、修改代码、观察验证反馈，并在失败时迭代。阶段化状态机同时限制无休止探索，并要求每一步留下可审计产物。

**面试回答要点**：ReAct 负责多轮决策；阶段化工作流把自由推理转化为可验证的工程流程。两者结合，既保留模型适应性，又控制工具权限、成本和终止条件。

## 第二章：工具调用为什么必须受控

Agent 不能直接获得宿主机或任意命令权限。RepoFixLab 的受信控制面独占 Docker 权限，只能按固定策略创建修复环境和评测环境；模型不能指定镜像、挂载、网络或系统能力。

受控验证也遵循同一原则：控制面从冻结的项目配置中生成允许的验证候选，模型选择候选而不是编写任意命令。这样能避免提示词注入、破坏性命令、测试篡改和“命令恰好绿了”的伪成功。

**证据**：74 轮正式运行中拦截 148 次受限操作，其中 42 次为沙箱逃逸尝试；未出现策略违规或逃逸放行。

**面试追问**：如果模型需要新工具怎么办？回答应包含申请、预检、权限、审计、批准、回滚，而不是直接开放 shell。

## 第三章：为什么修复环境与评测环境分离

修复 Worker 负责阅读和修改代码；它完成后被销毁。Evaluator 在新的容器中仅接收最终补丁，以固定官方 Harness 重新执行测试。分离的价值是避免模型通过修改测试、残留环境、缓存或运行时状态影响裁决。

最终结果包含：

- **F2P**：原本失败的目标测试是否变为通过；
- **P2P**：原本通过的测试是否仍然通过；
- **任务成功率**：一个任务只有全部 F2P 通过且没有 P2P 回归时才算解决。

不要把“本地测试通过”直接等同于“问题已修复”。广泛回归测试只能说明没有观察到某类回归；只有目标验收行为被证明，才能说明问题解决。

## 第四章：反馈、失败与迭代

验证反馈应当区分三种情况：补丁导致回归、目标行为尚未证明、环境或命令本身不可用。把它们混在一起会让 Agent 错误修复代码、重复调用工具或把失败环境解释为修复正确。

RepoFix 的迭代闭环是：候选补丁 → 基线/候选对照验证 → 结构化反馈 → 模型修订 → 新补丁 → 官方评测。失败样本同样保留，不能通过静默重试覆盖。

**面试回答要点**：好的 Agent 不只追求成功率，还要能区分“模型错了”“工具错了”“环境错了”，并为不同错误提供不同恢复路径。

## 第五章：评测、成本与可观测性

每次运行记录任务/环境/模型锁、补丁快照、验证记录、官方评测、令牌消耗、耗时和失败原因。这样可以复现某一次结果，统计模型调用成本，并定位失败发生在推理、工具、环境还是评测阶段。

在 26 个冻结真实 JavaScript/TypeScript 问题上：

| 方案 | 任务成功率 | F2P | P2P |
| --- | ---: | ---: | ---: |
| Pi 基线 | 21/26 | 29/32 | 587/592 |
| RepoFix 优化后 | 24/26 | 30/32 | 592/592 |

**面试提醒**：解释指标时先说明任务集合和评测方式，再说明结果；被问到失败案例时，能够解释目标行为没有实现、回归控制和环境失败之间的区别。

## 第六章：与 RAG、记忆的连接

代码修复 Agent 同样需要上下文工程：Issue、仓库文件、搜索结果、阶段产物和验证反馈不能无限塞入模型上下文。需要按任务相关性选择证据、压缩旧工具输出、保留关键约束，并防止旧信息污染当前决策。

面试时应能区分：

- **上下文管理**：当前任务的短期信息选择、摘要和压缩；
- **记忆**：跨轮或跨任务可复用的事实、偏好和经验；
- **RAG**：从外部知识库检索候选证据，再结合重排、引用和评测回答问题。

RAG 不是“向量库加模型”。需要讨论数据切分、嵌入、召回、重排、权限过滤、答案引用、离线评测和线上反馈。RepoFixLab 的官方评测思路可迁移到 RAG：先定义可验证任务和失败集，再优化检索或生成，而不是只看主观演示。

## 七天训练建议

| 天数 | 主题 | 产出 |
| --- | --- | --- |
| 1 | 项目 3 分钟介绍、ReAct | 60 秒与 3 分钟自述各一版 |
| 2 | 工具调用、状态机、终止条件 | 解释一次工具失败恢复 |
| 3 | 容器隔离、权限、安全 | 回答“为什么不能开放 shell” |
| 4 | F2P/P2P、离线评测、回归 | 解释指标与一个失败案例 |
| 5 | RAG、记忆、上下文工程 | 设计一个带权限过滤的检索系统 |
| 6 | Agent 系统设计 | 设计可观测、可恢复的多工具 Agent |
| 7 | 全流程模拟面试 | 完成复盘与薄弱点清单 |

## 开始练习

1. 用 60 秒回答：为什么 RepoFixLab 需要 ReAct 循环和阶段化工作流？
2. 用 90 秒回答：为什么必须让修复环境与官方评测环境分离？
3. 设计：如果 Agent 的工具调用连续失败，如何判断是模型、工具还是环境问题，并如何恢复？
