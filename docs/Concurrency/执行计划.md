# 高并发执行计划

本计划落实 [BACKGROUND.md](./BACKGROUND.md) 的场景和 [DESIGN.md](./DESIGN.md) 的方案。目标是在保持单任务执行语义不变的前提下，接收 1,000 个集中提交任务，将全局活跃任务严格限制为 200。本机验证参数见 [ACTUAL_IMPLEMENTATION.md](./ACTUAL_IMPLEMENTATION.md)。

## 固定决策

- PostgreSQL 是任务状态、队列顺序、幂等记录、租约、审计事件的唯一可信数据源。
- 首版不引入 Redis。进程内数据只用于短期读取加速，丢失后从 PostgreSQL 重建。
- Git 对象、依赖包使用本地只读内容缓存，缓存键使用内容哈希。任务可写目录保持独立。
- 单个调度器持有 PostgreSQL 领导租约。生产配置将 `WorkerPool` 硬上限固定为 200，因此全局活跃任务不会超过 200。
- 每个活跃任务持有独立工作区、Controller 运行实例、制品目录。现有 Controller 单实例容量保持为 1。
- 现有单任务 Agent、Worker、Evaluator 流程作为注入执行器复用，不把调度逻辑写入单任务流程。
- 首版使用先进先出队列，不实现任务优先级。
- 不修改前端。

## 模块解耦约束

```text
AdmissionService -> TaskStore <- TaskScheduler
TaskScheduler -> WorkerPool -> TaskExecutor
TaskExecutor -> WorkspaceManager
TaskExecutor -> ResultGate
LeaseManager -> TaskStore
ConcurrencyMetrics <- 状态事件
```

- `TaskStore`、`TaskExecutor` 是边界接口。业务模块不得直接访问 PostgreSQL 驱动、Controller 内部状态。
- `PostgresTaskStore` 只实现持久化语义，不决定调度顺序，不执行任务。
- `TaskScheduler` 只计算可出队数量，不创建工作区，不发布制品。
- `WorkerPool` 只控制并发和任务生命周期，不读取队列表。
- `WorkspaceManager` 只管理目录和只读缓存，不更新任务状态。
- `ResultGate` 只校验基线并发布不可变制品，不回收执行资源。
- `ConcurrencyMetrics` 只消费状态事件，不参与业务判断。

## 注释核心约束

所有新增、修改的生产脚本和测试脚本都使用精准简练中文注释。注释正文只允许以下三种格式。注释定界符只承担语言语法作用，不增加格式类别。

### 脚本级格式

放在文件首行，固定三项，每项一句。

```typescript
/**
 * 脚本职责：<本脚本唯一职责>
 * 输入边界：<允许读取的输入>
 * 输出边界：<允许产生的输出>
 */
```

### 类级格式

放在类声明前，固定三项，每项一句。

```typescript
/**
 * 类职责：<本类唯一职责>
 * 持有状态：<类内持有的状态>
 * 协作边界：<依赖的接口及禁止承担的职责>
 */
```

### 函数级格式

放在函数、构造函数、方法声明前，固定四项，每项一句。

```typescript
/**
 * 函数职责：<本函数完成的动作>
 * 输入约束：<参数前置条件>
 * 返回结果：<返回值及副作用>
 * 失败语义：<错误类型及状态影响>
 */
```

SQL 迁移脚本使用脚本级正文，并把首行定界符写为 `/*`。注释不得复述代码，不记录作者、日期、修改历史，不使用空泛描述。单项正文长度限制为 50 个汉字。

## WORKSTREAM1: 冻结并发契约与数据库结构

任务：定义任务状态、状态转换、失败原因、持久化接口和 PostgreSQL 表结构，先锁定模块间契约。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/contracts.ts`：定义 `ConcurrencyTask`、`TaskStatus`、`FailureCode`、`TaskExecutor`、`TaskExecutorFactory`，实现 `assertTaskTransition()`。
- 新增 `packages/repofixlab/src/concurrency/task-store.ts`：定义 `TaskStore` 接口，包含 `submit()`、`claimQueued()`、`transition()`、`heartbeat()`、`findExpiredLeases()`、`recordResult()`、`acquireSchedulerLease()`。
- 新增 `packages/repofixlab/migrations/001_concurrency.sql`：创建 `concurrency_tasks`、`concurrency_task_events`、`concurrency_scheduler_lease`。
- `concurrency_tasks` 使用幂等键唯一约束、单调入队序号、状态版本号、租约到期时间、基线提交、结果清单哈希。
- 状态更新统一校验上一版本号。版本不匹配时拒绝写入。

交付条件：

- badcase：两个事务同时把同一任务从 `running` 推进到不同状态，只有版本匹配的事务成功。
- badcase：`completed` 任务再次进入 `running`，契约层拒绝转换且数据库无新增状态事件。
- badcase：任务主记录更新失败，审计事件不得单独落库。

## WORKSTREAM2: 实现准入与 PostgreSQL 状态仓库

任务：实现集中提交、幂等准入、持久队列和原子状态写入。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/postgres-task-store.ts`：实现 `PostgresTaskStore`，所有状态变化使用数据库事务。
- 新增 `packages/repofixlab/src/concurrency/admission-service.ts`：实现 `AdmissionService.submit()` 和 `taskRequestSha256()`。
- 相同幂等键、相同请求哈希返回同一任务 ID。
- 相同幂等键、不同请求哈希返回固定冲突错误 `idempotency_key_conflict`。
- 数据库写入成功后才返回接收成功。数据库不可用时拒绝新任务，不在内存暂存。

交付条件：

- badcase：100 个并发请求使用相同幂等键和相同内容，数据库只生成 1 个任务，100 个响应返回同一任务 ID。
- badcase：相同幂等键提交两份不同内容，第二次提交返回 `idempotency_key_conflict`。
- badcase：提交事务在写入中断，任务主记录、队列记录、审计事件均不存在。

## WORKSTREAM3: 实现固定并发调度

任务：建立单领导调度、200 槽位 WorkerPool 和上游独立并发闸门。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/scheduler.ts`：实现 `TaskScheduler.start()`、`tick()`、`stop()`，只在持有领导租约时出队。
- 新增 `packages/repofixlab/src/concurrency/worker-pool.ts`：实现 `WorkerPool.submit()`、`availableSlots()`、`drain()`，构造时校验并冻结并发上限，生产值固定为 200。
- 新增 `packages/repofixlab/src/concurrency/capacity-gate.ts`：实现 `CapacityGate.acquire()`、`release()`，分别控制模型、Git、测试、制品写入并发。
- 新增 `packages/repofixlab/src/concurrency/task-executor.ts`：实现 `RepoFixTaskExecutorFactory.create()`、`RepoFixTaskExecutor.execute()`，为任务创建独立 Controller 运行实例并适配现有 `BatchRunExecutor`。
- 新增 `packages/repofixlab/src/runner/concurrent-batch-runner.ts`：实现 `executeConcurrentBatch()`，作为依赖组装入口。
- `claimQueued()` 使用事务和 `FOR UPDATE SKIP LOCKED`，按入队序号领取可用槽位数量。
- 排队任务不创建工作区，不启动 Controller。

交付条件：

- badcase：10 分钟内提交 1,000 个任务，活跃任务峰值等于 200，剩余 800 个任务保持 `queued`。
- badcase：第二个调度器同时启动，无法取得领导租约且领取任务数为 0。
- badcase：模型闸门测试容量设为 20，200 个活跃任务产生的模型并发峰值等于 20。
- badcase：任务执行抛出异常后槽位被释放，后续排队任务正常出队。

## WORKSTREAM4: 实现工作区与缓存隔离

任务：保证同仓库、同基线任务并发执行时不存在交叉写入，同时复用安全缓存。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/workspace-manager.ts`：实现 `WorkspaceManager.prepare()`、`verifyOwnership()`、`cleanup()`。
- 工作区固定使用 `<root>/workspaces/<task-id>`，制品暂存固定使用 `<root>/results/.staging-<task-id>`。
- Git 对象、依赖包缓存固定使用内容哈希目录，只读挂载到任务环境。
- 可写依赖缓存固定放入任务工作区，不跨任务复用。
- 缓存校验失败时删除该缓存条目并从可信源重建。任务状态不依赖缓存。

交付条件：

- badcase：200 个任务基于同一仓库和同一提交并发修改同名文件，源仓库内容保持不变，200 个工作区结果互不相同。
- badcase：只读缓存目录被任务写入，写入立即失败且其他任务继续执行。
- badcase：缓存条目哈希不匹配，任务重新构建缓存且不读取损坏内容。
- badcase：工作区回收失败，任务进入 `failed` 并记录 `workspace_cleanup_failed` 审计事件。

## WORKSTREAM5: 实现租约、心跳与故障恢复

任务：发现失联执行器，防止重复执行，并按 checkpoint 完整性决定恢复结果。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/lease-manager.ts`：实现 `LeaseManager.startHeartbeat()`、`stopHeartbeat()`、`recoverExpired()`。
- 租约有效期固定为 60 秒，心跳间隔固定为 20 秒。
- `recoverExpired()` 复用 `packages/repofixlab/src/runner/batch-state.ts` 的 `evaluateAttemptRecovery()`。
- checkpoint 完整且处于静止边界时继续同一 attempt；checkpoint 不完整时进入 `failed`，失败原因为 `checkpoint_incomplete`。
- 新执行器领取任务时使用状态版本号和租约所有者双重校验。

交付条件：

- badcase：执行器在 `running` 状态退出，时钟推进 61 秒后任务进入 `recovering`。
- badcase：两个执行器同时领取失效任务，只有一个执行器取得新租约。
- badcase：完整 checkpoint 通过绑定校验，任务继续原 attempt 且不会重复产生模型费用记录。
- badcase：缺少完整 checkpoint，任务进入 `failed` 并保留日志、工作区索引、失败原因。

## WORKSTREAM6: 实现结果门禁与不可变发布

任务：确保基线有效、证据完整、制品发布成功后才能写入完成状态。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/result-gate.ts`：实现 `ResultGate.verifyBaseline()`、`publish()`、`recordManifest()`。
- 复用 `packages/repofixlab/src/storage/artifact-store.ts` 的 `ArtifactStore.createNew()`、`writeNew()`、`publishTo()`。
- 最终目录固定使用 `<root>/results/<task-id>`，禁止覆盖已有目录。
- PostgreSQL 只保存结果清单路径、SHA-256、基线提交，不保存大体积日志和补丁正文。
- 当前目标分支提交与任务基线不一致时，任务进入 `revalidation_required`。
- 制品原子发布成功并写入结果清单后，任务才能进入 `completed`。

交付条件：

- badcase：结果发布成功前进程退出，任务保持 `publishing`，最终目录不存在半成品。
- badcase：目标分支在任务运行期间推进，补丁进入 `revalidation_required`，不得进入交付流程。
- badcase：两个执行器发布同一任务结果，第二次发布失败且首份制品字节不变。
- badcase：结果清单哈希与文件不一致，任务进入 `failed` 并记录 `result_manifest_invalid`。

## WORKSTREAM7: 接线、观测与场景压测

任务：完成模块组装、运行指标、故障注入和 1,000 任务验收。

具体实现：

- 新增 `packages/repofixlab/src/concurrency/metrics.ts`：实现 `ConcurrencyMetrics.recordTransition()`、`recordGateWait()`、`snapshot()`。
- 更新 `packages/repofixlab/src/runner/index.ts`、`packages/repofixlab/src/index.ts`：只导出并发入口和公开契约。
- 新增 `packages/repofixlab/test/concurrency/admission.test.ts`、`scheduler.test.ts`、`workspace-isolation.test.ts`、`lease-recovery.test.ts`、`result-gate.test.ts`、`load-profile.test.ts`。
- 指标只使用状态、阶段、失败原因作为标签。任务 ID 写入日志，不写入指标标签。
- 压测使用可控执行器，注入执行器退出、数据库短时中断、制品写入失败、目标分支推进。
- 验证顺序固定为：并发专项测试、`npm run check`、1,000 任务场景压测。

交付条件：

- badcase：1,000 个任务全部获得稳定任务 ID，活跃任务数始终不超过 200。
- badcase：数据库中断 30 秒，调度器停止领取新任务，不产生内存态完成记录；数据库恢复后继续处理队列。
- badcase：压测期间终止 20 个执行器，相关任务全部进入 `recovering`、`failed`、`completed` 中的确定状态。
- badcase：压测结束后，重复任务数为 0，交叉写入数为 0，同名制品覆盖数为 0，残留活跃租约数为 0。
- badcase：每个终态任务具有结果清单；失败任务具有固定失败原因和完整审计事件。

## 待确认

- PostgreSQL 生产版本、部署形态、连接池上限。
- 队列容量上限、单仓库并发上限、单租户并发上限。
- 单任务执行时限、排队时限、业务完成时限。
- 模型、Git、测试、制品存储的生产并发配额。
- 基线失效后的人工重新验证责任人和处理时限。

以上参数只影响配置，不改变模块边界、状态模型和开发顺序。
