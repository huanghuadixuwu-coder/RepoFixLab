# 高并发代码开发场景背景

## 文档目的

本文定义 RepoFixLab 在大厂代码开发环境中的高并发场景，说明业务压力、主要问题和设计边界。具体方案见 [DESIGN.md](./DESIGN.md)，实施步骤见 [执行计划.md](./执行计划.md)，本机验证见 [ACTUAL_IMPLEMENTATION.md](./ACTUAL_IMPLEMENTATION.md)。

## 场景设定

- 时间：大型版本发布前的集中修复窗口。
- 用户：500 名开发者。
- 仓库：50 个大型代码仓库。
- 任务：10 分钟内提交 1,000 个代码修复任务。
- 并发：平台同时执行 200 个任务，其余任务排队。
- 单任务流程：读取代码、调用模型、修改文件、执行测试、生成补丁、保存报告。
- 共享依赖：模型服务、Git 服务、依赖缓存、CI 资源、制品存储。

场景中的任务互相独立，但会集中争抢同一批基础设施。多个任务还可能基于同一仓库、同一提交点运行。

## 典型流程

1. 开发者提交代码修复任务。
2. 平台校验请求并生成稳定任务 ID。
3. 任务进入统一队列。
4. 调度器取得执行名额并创建独立工作区。
5. Agent 完成代码分析、修改和测试。
6. 平台保存补丁、日志、测试结果和资源账本。
7. 合并前检查目标分支是否已经变化。
8. 任务进入明确终态。

## 核心问题

### 1. 计算资源争抢

容器启动、依赖安装、测试进程会集中消耗 CPU、内存、磁盘空间和磁盘 IOPS。无并发上限时，整个平台会同时变慢。

### 2. 工作区互相污染

多个任务操作同一共享目录时，文件内容、Git 索引、依赖缓存和测试产物会互相覆盖，最终补丁失去可信度。

### 3. 重复执行

客户端重试、网络超时、执行节点重启会让同一请求被多次处理，造成重复模型费用、重复测试和重复补丁。

### 4. 上游服务承压

模型服务、Git 服务、CI 系统和制品存储都有容量上限。任务执行并发不能直接等于上游请求并发。

### 5. 任务状态丢失

执行节点退出后，任务可能长期停留在运行中。残留容器和临时目录会持续占用资源。

### 6. 补丁失效

任务执行期间目标分支持续推进。任务完成时，原始基线可能已经过期，补丁不能直接进入合并流程。

### 7. 结果互相覆盖

多个任务使用同名日志、补丁和报告路径时，后写结果会覆盖先写结果，审计链随之失效。

## 业务影响

- 开发者无法判断任务仍在排队、正在执行、已经失效。
- 相同任务产生不同补丁，结果缺少可信来源。
- 高峰期成本快速增长，完成时间不可预测。
- 共享仓库被污染后，后续任务继续继承错误状态。
- 补丁生成成功，但合并时才发现基线过期。
| 核心问题 | 具体触发场景 | 直接后果 |
| --- | --- | --- |
| 突发任务压垮系统 | 10 分钟提交 1,000 个任务，平台立即启动全部容器和测试进程 | CPU、内存、磁盘 IOPS 被打满，全部任务同时变慢并批量失败 |
| 重复执行 | 客户端等待超时后重试，平台缺少幂等键约束 | 同一任务重复调用模型、重复测试、生成多份补丁、重复计费 |
| 工作区污染 | 多个任务基于同一仓库，在同一可写目录执行 checkout、修改、测试 | Git 索引和文件互相覆盖，补丁混入其他任务内容 |
| 上游过载 | 200 个任务同时请求模型、Git、测试服务、制品存储 | 超过上游配额，出现限流、超时、连接耗尽 |
| 任务卡死 | 执行器运行期间退出，平台没有租约和心跳检查 | 任务长期停留在 `running`，槽位、容器、工作区无法回收 |
| 状态丢失 | 队列和执行进度只保存在进程内存，调度器重启 | 排队任务消失，运行任务无法恢复，结果无法绑定原任务 |
| 结果失效 | 任务执行期间目标分支产生新提交，原补丁仍按旧基线生成 | 补丁无法安全合并，测试结果不再代表当前代码 |
| 结果覆盖 | 多个任务将补丁和日志写入同一路径 | 后写结果覆盖先写结果，审计证据失真 |

## 本次设计范围

- 高并发任务准入与排队。
- 工作区隔离。
- 固定并发控制。
- 幂等执行。
- 状态租约与故障恢复。
- 补丁、日志、测试结果隔离。
- 合并前基线检查。
- 关键运行指标。

## 非目标

- 不改变单个 Agent 的阶段逻辑。
- 不改变前端风格和样式。
- 不设计自动合并主分支。
- 不在本阶段引入跨任务记忆共享。
- 不在本阶段实现代码。

## 待确认

- 模型服务、Git 服务、CI 系统的生产配额。
- 企业内部任务优先级规则。
- 排队时限、执行时限和业务完成时限。
- 补丁过期后的人工处理流程。
